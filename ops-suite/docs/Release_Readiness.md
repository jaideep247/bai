# Release readiness — gates, evidence and owners

> **First principle:** a positive result — *statement validated*, *file fully processed*, *health green*, *alert sent* — is issued only when the evidence for it exists; missing or unknown evidence is its own visible status.
> **Analogy:** a pilot's go/no-go — every gauge must be read, not assumed; a dark gauge is a no-go, not a green one.

Source: principal architecture review and the static repository audit (findings A01–A105). Code status refers to `main`; per-finding decisions and where each lives now: `history/Audit_History.md`.

**Scope of EBS in this release.** EBS validation runs **after** statement import, posting (FEBP) and payment clearing: a post-posting detective control (batch run `ZCD_EBS_VALIDATE`, FEB source). The whole suite is **read-only towards production data**: it reads SAP evidence and writes only its own records (runs, findings, exception history, suppressions, file registry, PRISM evidence). It has no pre-posting entry, no posting gate and no release of blocked lines; posting enforcement is a later phase with its own design and review (user decision 2026-11-07).

## 4. Configuration and exception control (production)

- Configuration changes: new entries only by customizing transport from DV1 — for every table, also deadlines, SLAs, calendar rows and alert rules (user decision 2026-11-07, design D-3) — existing entries edited in production with SCU3 change log and `ZCD_OPS` authorisation (configuration apps); runtime parameters in the framework app `ZUI_CA_PARAM` (definitions by transport only, values of released parameters in production, authorization object `ZCA_PARAM` per area, a refused value reported as `PARAM_INVALID`); effective-set checks reject missing required rules (A03) and colliding map rows (A98).
- Exceptions: assign / resolve / waive with reason, four-eyes for waivers and HCK suppressions, history per action (operations apps); owner and response window per critical control are maintained in the alert rules.
- Dynamic SQL: table / field allowlists enforced at the DAO execution boundary (FMON `ZCD_FMON_TABWL`, HCK whitelist re-validated at the SQL boundary); plug-in classes checked against their interface before instantiation (A62).
