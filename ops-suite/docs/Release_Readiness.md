# Release readiness — gates, evidence and owners

> **First principle:** a positive result — *statement validated*, *file fully processed*, *health green*, *alert sent* — is issued only when the evidence for it exists; missing or unknown evidence is its own visible status.
> **Analogy:** a pilot's go/no-go — every gauge must be read, not assumed; a dark gauge is a no-go, not a green one.

Source: principal architecture review and the static repository audit (findings A01–A105). Code status refers to `main`; per-finding decisions and where each lives now: `history/Audit_History.md`.

**Scope of EBS in this release.** EBS validation runs **after** statement import, posting (FEBP) and payment clearing: a post-posting detective control (batch run `ZCD_EBS_VALIDATE`, FEB source). The whole suite is **read-only towards production data**: it reads SAP evidence and writes only its own records (runs, findings, exception history, suppressions, file registry, PRISM evidence). It has no pre-posting entry, no posting gate and no release of blocked lines; posting enforcement is a later phase with its own design and review (user decision 2026-11-07).

## 4. Configuration and exception control (production)

- **Production configuration without transport (CAB / SOX note, user requirement 2026-11-07).** ZCD_FMON_DEADL, ZCD_FMON_SLA, ZCD_FMON_CAL and ZCD_OPS_ALRULE are production-maintainable: key users create new rows (deadlines, SLAs, expected files, alert rules) directly in PS4 — no customizing request, no CAB per change. Controls instead of the transport: (1) approval by role — only users with `ZCD_OPS` ACTVT 02 for FMON / CORE (production key-user role, granted through the access request process) can create; (2) every change is table-logged (SCU3, log flag on the tables, `rec/client`) and carries `LAST_CHANGED_BY` / `_AT`; (3) nothing can be deleted in PS4 (switched off with ACTIVE, history kept); (4) the morning report shows `CONFIG_CHANGED_IN_PROD` (information) for a changed production-maintainable table under drift control until the baseline is retaken; (5) mandatory back-port to DV1 on a customizing request within the week (`Operations_Runbook.md` §5h), referenced in the change ticket. The tables only decide *when and whom to alert* — none of them can change a posting, a payment or what EBS validates (read-only suite). CAB approves this standing change model once with the release; SOX evidence = SCU3 extract + back-port transport per change.
- Configuration changes: new entries by transport from DV1 (except the production-maintainable tables above), existing entries edited in production with SCU3 change log and `ZCD_OPS` authorisation (configuration apps); runtime parameters in the framework app `ZUI_CA_PARAM` (definitions by transport only, values of released parameters in production, authorization object `ZCA_PARAM` per area, a refused value reported as `PARAM_INVALID`); effective-set checks reject missing required rules (A03) and colliding map rows (A98).
- Exceptions: assign / resolve / waive with reason, four-eyes for waivers and HCK suppressions, history per action (operations apps); owner and response window per critical control are maintained in the alert rules.
- Dynamic SQL: table / field allowlists enforced at the DAO execution boundary (FMON `ZCD_FMON_TABWL`, HCK whitelist re-validated at the SQL boundary); plug-in classes checked against their interface before instantiation (A62).
