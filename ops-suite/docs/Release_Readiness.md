# Release readiness — gates, evidence and owners

> **First principle:** a positive result — *statement validated*, *file fully processed*, *health green*, *alert sent* — is issued only when the evidence for it exists; missing or unknown evidence is its own visible status.
> **Analogy:** a pilot's go/no-go — every gauge must be read, not assumed; a dark gauge is a no-go, not a green one.

Source: principal architecture review and the static repository audit (findings A01–A105). Code status refers to `main`; per-finding decisions and where each lives now: `history/Audit_History.md`.

## 1. "No positive result without evidence" — where the code now enforces it

| Positive result | Gap found | Now in code | Proof still needed (gate) |
|---|---|---|---|
| **Statement validated** | Failed rule passed silently; missing rules vanished; map actions lost; blank / missing trailers self-satisfied | Missing / unusable required rules are configuration findings (A03); BAI2 trailers never self-satisfied, missing trailers are B findings (A86, A95); CAMT detail sums, entry status and structure (A92–A94); a rule that could not run leaves its lines unevaluated, never passed (A66) | Gate 2 |
| **File fully processed** | Capped lot scan could prove completion; SLA met by another phase's event; overlapping runs overwrote newer state | Truncated scan is indeterminate (A38); SLA met only by its own stage, later stages are *inferred* (A40); per-payment ACK de-duplication (A39); version-checked registry writes (A04); file instance includes business date (A49, A90), one instance per file generation across midnight and daylight saving (design review 2026-11-07, `PRISM_Status_API.md` §7a); long file names keep their identity, digest verified against the full name (A100) | Gate 3 — shadow run with real PRISM / ACK feeds |
| **Health green** | Empty selection green; hung run hidden; flat baselines passed changes; partial G/L transfer evidence accepted | Empty or self-check-only selection is a configuration finding (A60); stale running runs detected independently (A06); flat-baseline tolerance (A59); G/L gaps per company with full population (A43); NO_DATA distinct from success (A68); baselines per series incl. DIM2 (A101); baseline warm-up is grey WARM-UP, never GREEN (A102); a silent expected company / source measures 0, a failed query is never zero (A103) | Gate 3 |
| **Alert sent** | BCS result ignored; claim after send; blocker lost behind a cap | BCS result checked (A45); durable claim before send with unique intent index (A17); severity-ordered caps (A63); status **S = submitted**, mailbox delivery is in SOST (A99) | Gate 3 — SOST reconciliation for payment-critical routes |

**Scope of EBS in this release.** EBS validation runs **after** statement import, posting (FEBP) and payment clearing: a post-posting detective control (batch run `ZCD_EBS_VALIDATE`, FEB source). The whole suite is **read-only towards production data**: it reads SAP evidence and writes only its own records (runs, findings, exception history, suppressions, file registry, PRISM evidence). It has no pre-posting entry, no posting gate and no release of blocked lines; posting enforcement is a later phase with its own design and review (user decision 2026-11-07).

## 4. Configuration and exception control (production)

- Configuration changes: new entries only by customizing transport from DV1 — for every table, also deadlines, SLAs, calendar rows and alert rules (user decision 2026-11-07, design D-3) — existing entries edited in production with SCU3 change log and `ZCD_OPS` authorisation (configuration apps); runtime parameters in the framework app `ZUI_CA_PARAM` (definitions by transport only, values of released parameters in production, authorization object `ZCA_PARAM` per area, a refused value reported as `PARAM_INVALID`); effective-set checks reject missing required rules (A03) and colliding map rows (A98).
- Exceptions: assign / resolve / waive with reason, four-eyes for waivers and HCK suppressions, history per action (operations apps); owner and response window per critical control are maintained in the alert rules.
- Dynamic SQL: table / field allowlists enforced at the DAO execution boundary (`ZCD_OPS_TABWL` filtered by area and purpose: FMON SOURCE, HCK READ re-validated at the SQL boundary); plug-in classes checked against their interface before instantiation (A62).
