# Known landscape tables — what the suite uses (source: USAA payment engine reference)

> **First principle:** only confirmed names go into configuration; anything else is marked and fails loudly at runtime (DDIC validation), never silently.
> **Analogy:** a map with surveyed roads drawn solid and rumoured tracks dotted — you plan the route on the solid lines.

Facts below were confirmed in production work in 2026 (payment engine reference). Where a money-moving decision rests on one, re-check it in SE11 / SE16 in QA1 and record what was checked.

## 1. Confirmed tables, fields and joins

| Table | Confirmed fields / rule | Join |
|---|---|---|
| `ZCD_PAYM_REQ_LOG` (payment requests from PRISM, API) | `ZZ_STATUS` — **take the row with `SUCCESS`, never the highest `COUNTER`** (a failed attempt can be written after the success); `COUNTER`; FIN number; `ZZ_MEMBER_NO`; `SOURCE` | FIN number = `DFKKOP-ZZ_FIN_TRANS_NUM`; `ZZ_MEMBER_NO` = `BUT000-BPEXT`, read **with** `SOURCE` first, then without (legacy PCLM partners pre-date SOURCE) |
| `ZCD_SPE_EXCP_LOG` (SPE) | Status-update table the hourly payment-status job sends from | **Every failure needs an SPE row**, otherwise the job never reports it to the source |
| `ZCD_CHECK_HIST` (IRIS cheque status via PRISM) | Status domain `ZECT_STATUS`: terminal **3 failed, 4 rejected, 9 returned**; mailed **10 → 9** allowed; otherwise a higher status may overwrite a lower one, **never the reverse**. PRISM translates IRIS "confirmed" to mailed | — |
| `DPAYH` | `ZZ_PAYMENT_STATUS` (live payment status) - **values confirmed by the user 2026-11-08:** `ISSUED` (file sent to the bank), `CONFIRMED` (bank acknowledgement received), `CLEARED`, `RETURNED`, `RETRIEVED`, `STOPPED` (cheques only: stop payment); the hourly payment status job updates them. **Applied 2026-11-08 (user decisions):** EBS R07 - BAI166D (ACH retrieval succeeded, no returns lot) expects `RETRIEVED`, BAI195D (wire return) `RETURNED`, BAI168D stays `RETURNED` (`EBS_VALIDATION.md`, parity D16 / D23); in-flight rules (`config/hck_seed.md` §8c) - D WIR / D ACH RETURNED and D ACH RETRIEVED need the status next to the bank evidence (`ISSUED` / `CONFIRMED` = not updated yet: in flight, `PAY_STATUS_LAG` after 120 min), D WIR / ACH CLEARED unchanged (`CLEARED`), a cheque with status `STOPPED` is VOIDED (state V or STOPPED, either alone; stopped and cashed = `CLEARING_INCONSISTENT` "stopped cheque cashed"); **stop and reissue (confirmed by the user 2026-11-08):** the reissue creates a new payment reference (new payment document / AUGBL) and a new cheque number - the stopped payment keeps `STOPPED`, the reissue is a separate payment with its own lifecycle; the status lag after the bank ACK uses `ISSUED` (`HCK_PAY_STATUS_ACK_OPEN`). Whether collections and cheques carry ISSUED / CONFIRMED is not confirmed (no status rows there); `LAUFD` + `LAUFI` give the cumulation group where `DOC1R` is not initial | `DFKKCR-DOC1R = DFKKOP-AUGBL` |
| `DFKKOP` | `ZZ_FIN_TRANS_NUM`; `ZZ_BILLPLANID` directly on DFKKOP (no DFKKNRK join); **clearing reason `AUGRD` 05 = reversal, the only reversal reason — confirmed by the user 2026-11-07** (constant `ZIF_CD_OPS_TRACE_TYPES=>GC_REVERSAL_AUGRD`, literal in `ZR_CD_TrxFlow`, compared by the parity check; VERIFY-SE11 field) | — |
| `DFKKNRK` / `DFKKNRP` (NOC lots) | `DFKKNRP` keys `MANDT`, `KEYN1` (lot), `POSNA` (item); `INFOF` CHAR 50 = the payment document (AUGBL) **or** the payment reference; **`FLGRD` = NOC reason** (confirmed by the user 2026-11-06; exact INFOF content and FLGRD length VERIFY-SE11). INFOF is not a key field (index VERIFY-SE11). Not an AML source | `DFKKNRP-INFOF` = `DFKKOP-AUGBL` / payment reference (R05, payment trace) |
| `DFKKRP` / `DFKKRAPT` | Exist (returns / clearing); **`DFKKRP-RLGRD` = return reason** (confirmed by the user 2026-11-06; VERIFY-SE11 length) | `DFKKRP-SELW1 = DFKKOP-AUGBL` |
| `FEBEP` | `BUDAT` always populated; `XBLNR` never blank for BAI 452; **`XBLNR` = bank text (letters, e.g. JPMC, BOA, PNC) + 10-character payment engine bank account + counter**, e.g. `JPMC8XX1174412334` → account `8XX1174412` (confirmed by the user 2026-11-06; the EBS scope and dashboard use it, `EBS_VALIDATION.md` §A0a); **carries no return / NOC reason** (confirmed 2026-11-06 — the reason is in DFKKRP-RLGRD / DFKKNRP-FLGRD) | `FEBEP-CHECT = BSEG-XREF2 = DFKKOP-AUGBL` (methods E G H I J K L); `DFKKCR-ZTNUM = FEBEP-CHECT` (method C) |
| `DFKKSUMC` / `DFKKKO` / `BSEG` | — | `DFKKSUMC-FIKEY = DFKKKO-FIKEY = BSEG-AWKEY` |
| `TFK042Z` | `XEINZ` separates collections from disbursements | — |
| `TFK033D` | Wildcard `*` does **not** work — enumerate | — |
| `TVARVC` | Refuses two type-P rows with the same name | — |

**Landscape facts (not tables)**

| Fact | Source | Where the suite applies it |
|---|---|---|
| **PRISM throttles ACH and wire files at 2 minutes per file before sending them to the bank; positive pay and stop pay are not throttled.** **One queue per bank** (JPMC, BOA, PNC … each wait 2 minutes between their own files; files to different banks do not wait for each other — confirmed by the user 2026-11-06, scope `C`); the gap is **1–2 minutes per file** (parameter default 2) and is measured from the PRISM status API timestamps (PRISM_RECEIVED → PRISM_DELIVERED) after go-live, then `FMON_PRISM_THROTTLE_MIN` is tuned. Files sent together (e.g. the evening ACH cycle) leave PRISM one at a time, so the time from PRISM's receipt to its delivery grows with the number of ACH / wire files queued ahead | Confirmed by the user 2026-11-06 | FMON SLA verdict of the delivery stage (`PRISM_DELIVERED` = `FORWARDED_TO_BANK`) and of later stages measured from generation: allowance = 2 min × files ahead in the PRISM queue (`FMON_FILE_MONITORING.md` §A3a; parameters `FMON_PRISM_THROTTLE_MIN` / `_SCOPE` / `_METHODS`, `FMON_PRISM_QUEUE_MAX`). Queue scope: one queue per bank (`FMON_PRISM_THROTTLE_SCOPE = C`, the delivered default and value row — confirmed 2026-11-06). **To confirm with the PRISM team:** does a retried / failed file re-enter the queue; is the 2-minute gap fixed or a minimum |
| **PRISM rejects a file whose name it has already received** — the file reference is unique per file generation (PRISM VERIFY item 1 closed) | User, confirmed 2026-11-07 | FMON file generation identity (`FMON_FILE_MONITORING.md` §A2 rules 8 and 9, `PRISM_Status_API.md` §7a) |
| **A file PRISM could not deliver (PRISM FAILED) is regenerated by SAP as another file with a new name for the same payments**, which PRISM delivers; the same for the cheque print file to IRIS when the PRISM → IRIS API call fails | User, confirmed 2026-11-07 | FMON regenerated files: generation group `ZCD_FMON_SRC-GROUP_FIELDS` / `ZCD_FMON_FILE-GEN_GROUP`, findings FILE_REPLACED, REGENERATION_MISSING, FILE_REGENERATED_NOT_FAILED, PRISM_DUPLICATE_NAME (`PRISM_Status_API.md` §7b) |
| **ECT cheque status (IRIS → PRISM → SAP): validated on `ZCD_CHECK_HIST` records with `ZCD_CHECK_HIST-STATE` = space (field STATE confirmed), linked by `ZCD_CHECK_HIST-ZTNUM = DFKKCR-ZTNUM`; `DFKKCR-STATE` is not checked; statuses 1, 3, 4 and 9 are reported** | User, confirmed 2026-11-07 | **Proposed, not built** (`FMON_FILE_MONITORING.md` §A4a) — open: which pay groups and sources have this behaviour (the user is confirming), meaning of status 1 |

`FEBEP-VB1OK` / `FEBEP-VB2OK` are the posted flags (posting area 1 / 2 — default of `EBS_FEB_POSTED_FIELDS`; confirmed by the user 2026-11-07). Field names **not** in the reference (still `VERIFY-SE11`): the FIN-number and timestamp fields of `ZCD_PAYM_REQ_LOG`, every field of `ZCD_SPE_EXCP_LOG`, every field of `ZCD_CHECK_HIST` other than the status domain and `STATE` (confirmed 2026-11-07; `ZTNUM` as the link to `DFKKCR-ZTNUM`, house bank / account fields and the change time stamp still VERIFY-SE11 — for the proposed ECT check), the ACK tables (`ZCD_ACH_ACK`, `ZCD_WIRE_ACK`), `ZCDT_REGUT` (incl. the payment-run fields `LAUFD` / `LAUFI` and the house bank used as `GROUP_FIELDS` of the generation group of regenerated files, and that one payment run + interface (+ house bank) gives exactly one file per generation — 2026-11-07), `ZCD_STRP_POUT_LOG`, `ZCD_ACH_RTRV_LOG` status field (three candidate names, parity C4).

## 2. How the suite uses them (phase 3 of the RAP build) — **built 2026-11-06**

| Use | Payment engine area | Known facts applied | Still to confirm |
|---|---|---|---|
| PRISM payment-request monitoring (API interface `PAYREQ_PRISM_IN`) | FMON (generic adapter, configuration) | Status field `ZZ_STATUS`, processed = `SUCCESS`; a later failed row must not downgrade a request that has a SUCCESS row; partition by `SOURCE` | Request reference / FIN-number and timestamp field names |
| Payment request failed **without an SPE row** | HCK check (new check class) | Every failure needs a `ZCD_SPE_EXCP_LOG` row | SPE key field linking to the request |
| Cheque status went **backwards** (illegal transition) | HCK check (new check class) | `ZECT_STATUS` ordering, terminal 3 / 4 / 9, 10 → 9 allowed | `ZCD_CHECK_HIST` key and sequence fields |
| Paid payment request left **CANCELLED** (PCLM) | HCK check (new check class) | CANCELLED = money will not leave; a paid request must never be CANCELLED | Paid indicator (via FIN number → DFKKOP / DPAYH) |
| Handled-manually record for payment requests | FMON operations app (§6.5 of `RAP_Apps_Design.md`) | Request reference as delivered by PRISM | — |
| EBS: BAI 143 / 452 | EBS | Known unmapped codes in production | **Built (2026-11-06):** 143 → rule group BAI166C on collection accounts only (disbursement stays blocked by R14); 452 → BAI468D |
| 360° payment trace (`ZCD_OPS_PAYMENT_TRACE`, **built 2026-11-06**, `Payment_Trace.md`) | Core (read-only) | SUCCESS row, never highest COUNTER; FIN = `DFKKOP-ZZ_FIN_TRANS_NUM`; partner with SOURCE first, then without; FEBEP-CHECT = AUGBL (E G H I J K L) / ZTNUM (C); DFKKCR-DOC1R = AUGBL; DFKKRP-SELW1 = AUGBL; DFKKSUMC/DFKKKO/BKPF FIKEY; TFK042Z-XEINZ; ZECT_STATUS 3/4/9 | DFKKRAPT history fields, ZCDT_REGUT LAUFD/LAUFI → file key, request FIN / time fields, ACK payment key, `DFKKOP-AUGRD` / `DFKKKO-STBEL` (reversal), BUT000 source field |
| EBS: BAI 452 has a non-blank XBLNR | EBS (rule R-level check once mapped) | `XBLNR` never blank for 452 | — |
| EBS: payment engine account scope (**built 2026-11-06**) | EBS engine + dashboard | Account = XBLNR without leading letters, first 10 characters; statement validated / shown only when every line's account is an active `ZCD_EBS_ACCT-ACCOUNT_NO` | Layout on a production sample of each bank; ACCOUNT_NO values maintained in upper case |

Every field name above that is not confirmed goes into configuration (not code) and is validated against the DDIC at runtime, so a wrong name produces a PLUGIN_ERROR / configuration finding instead of a wrong result.
