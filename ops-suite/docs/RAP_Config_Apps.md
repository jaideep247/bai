# RAP configuration apps — EBS, file monitoring, health check, alerting

> **First principle:** configuration decides what blocks a payment, so it is changed through an app that checks every value, knows which client it is in, and leaves a transport or a change log behind.
> **Analogy:** one control panel per signal box — each team gets its own panel (app), every switch (field) is interlocked (validation), and the panel knows whether it is in the workshop (DV1, changes go on a transport) or on the live line (PS4, only adjust existing switches).

Implements design §5 (`RAP_Apps_Design.md`, decisions D-2, D-3). Status: generated and statically checked offline (abaplint: CDS, BDEF and ABAP parsed; 0 issues). **Not yet activated in SAP** — first DV1 import is the test.

**Runtime parameters are not maintained here** (2026-11-07): the OpsParam section (table ZCD_OPS_PARAM, draft table ZCD_D_PARAM, entities `ZR_/ZC_CD_OpsParam`) is retired. Parameters live in the global framework `ZCA_PARAM` and are maintained in its app *Parameter areas* (`ZUI_CA_PARAM_O4`, `param-framework/docs/ONBOARDING.md`), areas `CD_OPS`, `CD_EBS`, `CD_FMON`, `CD_HCK`; the framework has its own transport / production rules (definitions by transport only, values of released parameters adjustable in production).

Shape — SAP's business-configuration maintenance object (verified against `SAP-samples/abap-platform-refscen-flight`, branch `ABAP-platform-2023`, carrier singleton):

- **Singleton root** `ZR_CD_<Mod>CfgAll`: `key 1 as SingletonID` over `I_Language`; virtual (`with unmanaged save`, nothing persisted); `lock master`, `total etag LastChangedAtMax`, draft table `ZCD_D_<MOD>CFG`; carries the field **TransportRequestID** (customizing request, DV1).
- **Total ETag** `LastChangedAtMax` = `max( LastChangedAt )` over the change-stamp view `ZI_CD_<Mod>CfgChg` (UNION ALL of `LAST_CHANGED_AT` of all tables of the app).
- **Children** `ZR_CD_<Alias>`: managed, `persistent table` = the customizing table, own draft table `ZCD_D_*`, `lock dependent`, `authorization dependent`, `etag master LocalLastChangedAt`, `with additional save` (transport recording), explicit `mapping for`.
- Projections `ZC_CD_*` (`provider contract transactional_query`), metadata extensions `ZC_CD_*` (DDLX: one table section per child on the object page, list + identification per table), projection BDEFs `ZC_CD_<Mod>CfgAll`.
- Behaviour pool `ZBP_R_CD_<MOD>CFGALL`: thin handlers, every decision in `ZCL_CD_OPS_CFG_GATE` / `ZCL_CD_OPS_CFG_CHECKS`.
- Every customizing table got `LAST_CHANGED_BY` (`abp_lastchange_user`), `LAST_CHANGED_AT` (`abp_lastchange_tstmpl`), `LOCAL_LAST_CHANGED_AT` (`abp_locinst_lastchange_tstmpl`), filled by the RAP framework; engines and DAOs ignore them. Existing `CHANGED_BY` / `CHANGED_AT` (SM30 era) are read-only and hidden.

All artefacts are generated by `tools/rap_generate.py` from the table DDLs and a small spec (aliases, labels, checks); `tools/abapgit_serialize.py` writes the abapGit XML. Regenerate both after a table change.

## 2. Change policy (D-3) — `ZCL_CD_OPS_CFG_POLICY`

Client settings come from T000 (SCC4) through `ZCL_CD_OPS_CFG_CLIENT`; an unreadable client is treated as production (fail closed).

| Client (T000) | Create | Update existing | Delete | Customizing request |
|---|---|---|---|---|
| Automatic recording of changes (`CCCORACTIV = 1`) — DV1 customizing client | yes | yes | yes | **required**; open customizing request or task; every change recorded |
| Changes without recording (`' '`) — sandbox | yes | yes | yes | not checked, not recorded |
| No changes allowed (`2`) / no transports (`3`) — QA1 | **no** | **yes**, direct, change-logged | **no** | none |
| Role production (`CCCATEGORY = P`) — PS4, whatever the change option | **no** | **yes**, direct, change-logged | **no** | none |

### One policy for every table (user decision 2026-11-07)

**New configuration rows reach production only by customizing transport from DV1** — also deadlines, SLAs, calendar rows and alert rules; there is no per-table exception and no direct create in production. In QA1 / PS4 support may only **edit existing rows** (direct, change-logged: SCU3, `LAST_CHANGED_BY` / `_AT`), never create or delete.

Tables with an `ACTIVE` flag — production can switch a row off by editing it (no delete needed), and every reader honours the flag:

| Table | App / entity | Reader filtering `ACTIVE` |
|---|---|---|
| ZCD_FMON_SLA | File monitoring / FmonSla (durations and deadlines) | `ZCL_CD_FMON_DAO->GET_SLAS` (field 2026-11-07; both kinds, 2026-11-08) |
| ZCD_FMON_CAL | File monitoring / FmonCalendar | `GET_CALENDARS` (field 2026-11-07) |
| ZCD_OPS_ALRULE | Alerting / AlertRule | `ZCL_CD_OPS_ALERT_DAO->GET_RULES` (field existed) |

- Health check drift (`ZCD_OPS_TABWL` rows HCK / DRIFT): these four tables are under drift control (`config/hck_seed.md` §6) — a production edit of an existing row (due time, severity, `ACTIVE`, SO23 list) is reported as `CONFIG_DRIFT` like any other table until the change is back-ported to DV1 and the baseline is taken again; that is exactly what drift control should show.
- A new deadline or similar alert: `Operations_Runbook.md` §5h (DV1 → QA1 → PS4).

- Create / delete are switched off by **global feature control** (button greyed out), not by an error after the fact.
- **VERIFY-SE11:** the fixed values of domain `CCCORACTIV` (`ZIF_CD_OPS_CFG_TYPES=>GC_CHANGE_OPTION`) before activation; one constant to change if they differ.
- Production changes are logged by **table change logging** (log flag on all 27 customizing tables of the apps; Basis sets `rec/client`), visible in SCU3.

### Request check (DV1)
`ZCL_CD_OPS_CFG_GATE->CHECK_REQUEST` reads E070 and refuses (validation `validateTransport` on every child, also for deletions): no request (402), unknown request (403), not a customizing request / task — e.g. a workbench request (404), released or no longer modifiable (405).

### Transport recording (DV1)
`save_modified` passes `REF #( create / update / delete )` and the entity ↔ table relations to `ZCL_CD_OPS_CFG_TRANSPORT`, which calls SAP's business-configuration CTS API for RAP (`MBC_CP_API=>RAP_TABLE_CTS( )->RECORD_CHANGES( )`). If recording fails the save is aborted with a short dump (`RAISE SHORTDUMP`) — changes are never kept unrecorded on a recording client.

## 3. Authorisation

`authorization master ( global )` on each root: `ZCD_OPS` with `ACTVT 02` and `ZCD_PE_AREA` = the app's payment engine area covers update, Edit and create-by-association of every child. Read access is granted by the service (start authorisation `S_SERVICE` through the business role / PFCG); CDS access control is `#NOT_REQUIRED` (customizing, no company-code data). The check runs through the adapter `ZIF_CD_OPS_CFG_AUTH` / `ZCL_CD_OPS_CFG_AUTH`, which delegates to `ZCL_CD_OPS_AUTH` (design §1).

**Pattern fields (user decision 2026-11-06).** Generator check `('pcre', field)` in `tools/rap_generate.py` → `ZCL_CD_OPS_UTIL=>PCRE_VALID` (the one helper also used at runtime): the pattern must compile as PCRE (it is matched to the complete value, case ignored; blank allowed), else message 418 on the field. The suppression operations app checks its key pattern the same way (`ZCL_CD_HCK_SUPPRESSION=>CHECK_REQUEST`). Pattern lists inside ZCD_HCK_DEF parameters are not validated by the app (the same PARAM columns hold numbers for other checks) — the check raises E373 at runtime and `ZCD_OPS_PATTERN_CHECK` shows them. VERIFY-ADT: validation messages on the draft in Prepare / Activate (no offline RAP runtime; the generator fixture tests cover the template and the list of validated fields).

Names are checked for DDIC syntax (letters, digits, `_`, `/`) **before** the dictionary is asked, so no free text reaches RTTI. Keys are read-only after create; keys that may be blank (BTC map bank key = default row, flow-pattern priority, status value) are not mandatory.

## 7. What the design said and what differs

| Design §5 | Built | Why |
|---|---|---|
| Transport API `mbc_cp_api` | Same, isolated in one class, `VERIFY-ADT`; fallback named (`TR_OBJECTS_CHECK` / `TR_OBJECTS_INSERT`, `VERIFY-SE37`) | Signature not verifiable offline |
| Total ETag = max of the children's `LAST_CHANGED_AT` | Via a UNION ALL change-stamp view per app | A join of all tables to the root would multiply rows (cartesian); the union stays one row per table row |
| Authorisation through `ZCL_CD_OPS_AUTH` | Adapter `ZCL_CD_OPS_CFG_AUTH` (same object and fields) delegating to `ZCL_CD_OPS_AUTH` | The configuration apps keep their own injectable seam |
| Validation "rule group has at least one active rule" | Implemented across the drafts of the same edit session | — |
| "Quiet-hours window valid", "cron-free" | Window both-or-neither (crossing midnight allowed); there are no schedule fields to check | — |
