# Process catalogue — the suite's customer layer and the activation proposal

> **First principle:** the framework's catalogue knows the SAP standard processes; the suite says which of them the
> payment engine runs today, adds its own process (collections request lifecycle of BASE) and maps the monitoring it
> already has - and nothing it does not run shows on a dashboard.
> **Analogy:** the hotel's room plan from the architect (every room exists) with the housekeeping board on top: the
> rooms in use are lit, the rest stay dark until the manager signs them into service.

Concept, model, activation rule, runtime behaviour and authorisation: `ops-framework/docs/PROCESS_CATALOGUE.md`.
Customer layer spec: `config/catalogue/overlay.json` (package `CD`, kind C, rank 100, prefix `CD_`). Generated by
`tools/process_catalogue.py`: `config/catalogue/seed/*.csv` (rows of the layer), `docs/catalogue/catalogue.md` (every
process of the four packages with this landscape's state and monitoring) and `docs/catalogue/activation.md` (the
activation proposal and the decision list). Status 2026-11-11: written and checked offline; **nothing activated, no
activation approved** - every row below is a proposal until the business approver is entered in DV1.

## 1. Activation proposal (to confirm with the business)

Rule applied (user, 2026-11-11): **ACTIVE only the processes the suite already monitors**; everything else
INACTIVE with "to confirm with business". The proposal rows are effective from 2026-11-11; the approver is entered in
DV1 (four-eyes - never the user who saves; message 240).

| Process | Proposal | Monitored today by |
|---|---|---|
| `S4_BATCH_JOBS` background job processing | ACTIVE (product default) | business process `CD_JOBS` / `SAP_JOBS` (framework job monitor, `CAT_PROCESS` = `S4_BATCH_JOBS`); morning report `E_JOBS` |
| `S4_BANK_STMT` electronic bank statement | ACTIVE (row) | EBS validation (`CD_EBS`, BAI2 / CAMT); morning report `B_VOL_STMT`, `A_RECON_3WAY` |
| `FICA_PAYRUN` payment run (disbursements and collections) | ACTIVE (row) | morning report `A_INFLIGHT`, `A_PRQ_NOT_PAID`, `B_VOL_PAYRUN`, `C_CHQ_STATUS`; payment trace; FMON payment files |
| `FICA_RETURNS` returns lots | ACTIVE (row) | morning report `A_RET_AGED`; ACH return files (FMON) |
| `FICA_GL_TRANSFER` G/L transfer and reconciliation keys | ACTIVE (row) | morning report `A_GL_TRANSFER`, `A_RECON_3WAY`; ledger drill-down |
| `CD_COLL_REQ_LIFE` collections request lifecycle (BASE) - customer process | ACTIVE (default of the layer) | business process `CD_COLL` / `BASE_REQ_LIFE` (checks R1-R4, inactive until V130) |
| every other process of FICA and FSCD (18) | inactive - to confirm with business | `FICA_REVERSAL` is partly watched by `A_DOC_CHANGE` (reversals of payment documents only) |

Effect in this landscape: the active product processes are monitored by the suite's own engines (morning report,
EBS validation, FMON, payment trace), not by checks of the framework's runner - so the catalogue changes nothing in
those engines. It changes:

- the framework's runner for the two business processes that name a catalogue process: `CD_JOBS` / `SAP_JOBS` keeps
  running (`S4_BATCH_JOBS` active by default), `CD_COLL` / `BASE_REQ_LIFE` stays inactive (its row and checks are
  inactive until V130; when activated it runs while `CD_COLL_REQ_LIFE` is active);
- the area dashboard (*Active business processes*, *Process catalogue*) and the overview cards of
  `ZUI_CA_OPS_DASH`: only the active processes;
- the morning report's onboarding check (`D_PROC_ONBOARD`, adapter of `ZCL_CA_OPS_CHK_ONBOARD`): the new catalogue
  findings. Expected at go-live until the decisions are taken: `CAT_NO_CHECK` (W) for the five active product
  processes and `CD_COLL_REQ_LIFE` (no framework check in effect monitors them - their monitoring is the suite's own
  engines; see decision D-CAT3), and 253 for the activation rows until the approver is entered.

## 2. What the layer holds

| Object | Content |
|---|---|
| package `CD` | customer layer of the payment engine, rank 100, prefix `CD_`, owner PE RTB |
| process `CD_COLL_REQ_LIFE` | collection requests of BASE via PRISM: PENDING, account validation, SCHEDULED, answer of the source, collection by `FPY1`, Stripe refund of a rejected card payment; table and programs are V130 placeholders; depends (hard) on `FICA_PAYRUN` |
| `monitoring` | `CD_JOBS` / `SAP_JOBS` monitors `S4_BATCH_JOBS` (`config/process_register.csv` column `CAT_PROCESS`) |
| `external` | the suite's own monitoring of each active process (table above), documented only |
| `activation` | four rows (payment run, bank statement, returns, G/L transfer), effective from 2026-11-11, reason "In use; monitored by the suite since go-live (proposal - confirm with business)", approver entered in DV1 |
| `decisions` | the decision list (§3) |

`config/process_register.csv`: `CAT_PROCESS` = `CD_COLL_REQ_LIFE` for `CD_COLL` / `BASE_REQ_LIFE`, `S4_BATCH_JOBS` for
`CD_JOBS` / `SAP_JOBS` (checked offline: the catalogue process exists and the layer maps the same pair).
