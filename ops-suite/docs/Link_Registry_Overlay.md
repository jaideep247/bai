# Link registry — the suite's customer overlay and the migration of its link definitions

> **First principle:** the framework's registry knows how SAP standard objects link; the suite adds only what is this
> landscape's own — its `ZCD_*` tables and `ZI_CD_*` views, its custom fields on standard tables and the links between
> them — and every table-to-table link the suite needs is defined once, with its evidence.
> **Analogy:** the city's own bus routes drawn on a transparent sheet over the publisher's map: the streets stay the
> publisher's, the routes and stops are the city's, and a route that is not surveyed yet is drawn dotted.

Concept, model, validation and walker: `ops-framework/docs/LINK_REGISTRY.md`. Overlay spec:
`config/links/overlay.json` (layer `CD`, kind C, rank 30, prefix `CD_`). Generated by `tools/link_registry.py`:
`config/links/seed/*.csv` (rows of the overlay), `docs/links/lineage.md` (all three layers, diagram and custom field
flows), `docs/links/cds_snippets.md`, `docs/links/impact.md` (fields → links, object keys, payment model sections,
aggregate checks). Facts: `USAA_Known_Tables.md`. Status 2026-11-11: written and checked offline; **nothing activated**.

## 4. How the suite changes a link

1. Edit `config/links/overlay.json` (a field confirmed in SE11: replace the placeholder, evidence `C`, link `active`).
2. `python3 tools/link_registry.py` (seed rows, lineage, snippets, impact) and `--check`; the payment model:
   `python3 tools/payment_model.py` when a join it names changed (the generated views change only then).
3. DV1, customizing request: the changed rows in `ZUI_CA_OPS_CFG` (`ZCA_OPS` `CA_OPS` 01 / 02 / 06 - the configuration
   role, DV1 only); `ZCA_OPS_TABWL` rows of area `CD_OPS` for every source a walk reads.

## 6. Decisions for the user

1. **Seed delivery**: the registry rows are created in DV1 in the configuration app from the generated CSV (as the
   parameter definitions). An upload report for seed rows is not built - decide whether one is wanted.
2. **Composite joins** (`Pm`, `RcSet`) stay CDS text in the payment model mapping; a registry concept "link over two
   source objects" was not added (it would need two sources per read in the walker).
3. **Trace and file monitor** keep their own link definitions until V122; then decide per reader whether it reads the
   registry (the trace's cheque link would need the house bank account restriction as a registry link of the
   bank statement header, V117).
4. **Registry check in the morning run**: register `ZCL_CA_OPS_CHK_LINKS` in area `CD_OPS` (a registered process needs
   its control, alert rule and owner - process onboarding) or run it on demand only.
