# Implementation order — DV1 activation and transport

> **First principle:** activate what others depend on first, and ship each payment engine area as one object set — a runtime switch cannot protect against an inactive class.
> **Analogy:** building a house — foundation (DDIC), walls (interfaces), wiring (classes), then switching the power on (customizing and jobs).

Landscape DV1 → QA1 → PS4. Packages `ZCD_OPS` with sub-packages `ZCD_OPS_CORE`, `ZCD_OPS_EBS`, `ZCD_OPS_FMON`, `ZCD_OPS_HCK`.

**abapGit import (recommended).** The repository carries `/.abapgit.xml` (starting folder `/ops-suite/src/`, folder logic PREFIX) and full abapGit metadata: packages, classes, interfaces, programs with text pools, **all 66 tables** (65 of the posting-area build plus `ZCD_PAY_OUTPKG`, 2026-11-08; incl. draft tables and their secondary indexes), CDS / BDEF / DDLX / service definitions of the RAP apps and the message class `ZCD_OPS`. Create the transportable package `ZCD_OPS` in DV1 with the landscape's transport layer, link the repository in abapGit (online: `https://github.com/jaideep247/bai.git`, or offline: `git archive --format=zip -o bai-ops-suite.zip <commit>` → Import ZIP), pull and assign a Workbench request. abapGit activates in dependency order, which replaces most of Steps 1–2 below; use them as the manual fallback and as the checklist for what must be active. Metadata is regenerated with `python3 tools/abapgit_serialize.py`.

**Parameter framework first.** The suite reads every runtime parameter from the global framework `ZCA_PARAM` (`param-framework/`, package `ZCA_PARAM`, own abapGit import from starting folder `/param-framework/src/` — `param-framework/README.md`). Install and activate it **before** the suite (the suite's classes reference `ZIF_CA_PARAM`, `ZCL_CA_PARAM_FACTORY`, `ZCX_CA_PARAM`; the unit tests `ZCL_CA_PARAM_DAO_MEM` / `_BUILDER` / `_INJECTOR`), then register the suite's areas and import its definitions (step 3.0). ZCD_OPS_PARAM no longer exists; it was never deployed, so there is **no migration report** — values are entered in the framework app.

**Operations framework second (2026-11-10).** The suite's store, exceptions app, alerting, run lock / guard, configuration gate, retention purge and utilities are the separate component **ZCA_OPS** (`ops-framework/`, package `ZCA_OPS` + `ZCA_OPS_UI`, own abapGit import: offline ZIP `git archive HEAD:ops-framework --format=zip -o zca_ops.zip`, starting folder `/src/` of that folder - `ops-framework/README.md`). Install order **ZCA_PARAM (1.1.0 or later) -> ZCA_OPS -> suite**; ZCA_OPS refuses every run on an older ZCA_PARAM (message ZCA_OPS 044). After the pull: area `CA_OPS` and the 15 definitions of `ops-framework/config/param_definitions.csv` (step 3.0; 11 + the control review's `CONTROL_TIME_ZONE`, `CONTROL_TEAMS`, `RETENTION_DAYS_REVIEW` and the exception reason codes `EXC_REASON_CODES`, 2026-11-10), service bindings `ZUI_CA_OPS_EXC_O4` and `ZUI_CA_OPS_CFG_O4`, `ops-framework/docs/VERIFY.md`. User decisions of 2026-11-10: prefix `ZCA` kept, ZCA_PARAM and ZCA_OPS separate components shipped together, one area register (`ZCA_PARAM_AREA`; the suite's areas are `CD_EBS`, `CD_FMON`, `CD_HCK`, `CD_OPS`, was EBS / FMON / HCK / CORE), one authorisation object `ZCA_OPS` replacing `ZCD_OPS` (field `ZCA_PARAR` replacing `ZCD_PE_AREA`; nothing was activated, so nothing to migrate).

**Pin the revision.** Pull one reviewed commit and record its SHA in the transport description; SAP can only pull what is pushed to the remote (use the offline ZIP otherwise).

**Read-only rollout scope.** The suite observes and reports: EBS validation after statement import, posting and payment clearing; FMON; HCK; the payment trace. It never writes FS-CD / FI data and has no posting gate, line release, reprocessing navigation or outbound webhook (removed 2026-11-07; enforcement is a later phase with its own design). Its only writes are its own records — runs, findings, exception history, suppressions, file registry, PRISM evidence. Kept outside the switch-on:
- the **PRISM status API** (step 1e): its table and classes are transported, the SICF node is created **inactive** and the PRISM technical user gets no role — a new callback is outside the read-only rollout and is switched on only as its own CAB-approved change (switch **S-PRISM**).

1. **FILE (client-independent, workbench request):** logical path `ZCD_OPS_EBS_IN` (directory of the bank files EBS may read before import, physical path `<dir>/<FILENAME>` per operating system) and `ZCD_OPS_HCK_OUT` (directory of the morning report CSV export); logical file names `ZCD_OPS_EBS_IN` / `ZCD_OPS_HCK_OUT` assigned to them (used by `FILE_VALIDATE_NAME`). Merge 7: the key change does not break the class lookup by payment method - only class rows (HBKID blank) carry payment methods and ageing basis (enforced by the app: a house-bank row needs a CALENDAR and must leave PAY_METHODS / AGE_BASIS blank), and the payment outcome maps methods from the class rows alone (`ZCL_CD_OPS_PAY_OUTCOME=>LOAD`), so a method still belongs to exactly one class per flow (message 385 unchanged). The house bank only overrides the calendar: resolution row of the payment's house bank, then the class row's calendar, then PARAM1 of the check, then none (`INFLIGHT_CONFIG` W) - unchanged. A separate CALENDAR-override key was therefore not needed.
